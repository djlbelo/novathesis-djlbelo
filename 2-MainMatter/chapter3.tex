\chapter{System Description and Methodology}
\label{cha:system-description}

This chapter describes the technical platform on which the research
contributions are built and the methodology governing their design,
implementation, and evaluation.
Section~\ref{sec:system-description} characterises Maestro - the Closer
\gls{genai} Framework - in its pre-intervention state and identifies the structural
gaps that motivate each objective. Section~\ref{sec:methodology} formalises the
research approach and the evaluation instruments applied to each objective.

% ============================================================
\section{System Description}
\label{sec:system-description}
% ============================================================

\subsection{Overview and Architectural Pattern}
\label{subsec:overview}

Maestro is a multi-repository, microservices-based
\gls{rag} platform for deploying enterprise \gls{genai} applications~\cite{closer2025maestro}.
Although the \gls{llm} gateway is designed to abstract multiple model providers,
all production deployments evaluated in this work operate on Microsoft Azure.

Independent FastAPI services communicate over HTTP with API-key authentication
in a REST/JSON service mesh, with no message queue or event bus mediating
inter-service calls.
Service URLs are resolved through Azure App Configuration, secrets through
Azure Key Vault, and all Python services share a base Docker image distributed
via a shared Azure Container Registry.
Infrastructure is provisioned declaratively with OpenTofu, and continuous
integration and delivery are handled through Azure DevOps Pipelines.

The framework is implemented in Python~3.12 using FastAPI, LangChain, and
Streamlit.
As discussed in Section~\ref{sec:orchestration-frameworks}, LangChain provides
Maestro's current orchestration primitives, a design decision that directly
informs O4.
Before this work, the platform decomposed into four core runtime microservices,
three user-facing surfaces, and two platform-layer repositories; this work adds
a fifth core runtime service, the \gls{mcp} gateway (\texttt{chatbot-mcp}).
The resulting set is summarised in Table~\ref{tab:service-tiers}.

This research focuses on the core runtime microservices - the four original
ones and the \gls{mcp} gateway added by this work; the
user-experience surfaces and the optional guardrails service are not modified
and are described only as needed to characterise the system.

\subsection{Core Services}
\label{subsec:core-services}

\paragraph{Chatbot Backend (\texttt{chatbot-backend}).}
The backend is the sole orchestrator of the \gls{rag} pipeline and the single contact
point for all frontend surfaces.
It implements the full golden-path sequence - conversation-history retrieval,
hybrid vector search, per-chunk relevance filtering, prompt assembly, and \gls{llm}
invocation - through hand-crafted, non-composable orchestrators, each a
standalone script with no shared primitive for branching, parallelism, or
execution tracing.
As established in Sections~\ref{subsec:rag_survey}
and~\ref{sec:orchestration-frameworks}, this is characteristic of
Naive-to-Advanced \gls{rag} pipelines that predate composable agent-graph runtimes;
O4 addresses it by refactoring the orchestrators as reusable LangGraph
graphs~\cite{chase2022langchain}.
The \gls{rag} path is therefore a fixed pipeline: it has no thought-and-action
loop, and only the tool-selection rounds introduced with \gls{mcp} (Section~\ref{subsec:connectivity})
iterate in a \gls{react}-like manner.
In its pre-intervention state, the service also performed no cost or
token-consumption instrumentation, the structural gap addressed by O2.

\paragraph{\gls{llm} Microservice (\texttt{llm-microservice}).}
This service is a provider-agnostic \gls{llm} façade, routing generation requests to
Azure OpenAI, OpenAI, Azure AI Services, and Google Gemini behind a stable
internal \gls{api} contract.
A routing registry (\texttt{REQUEST\_PER\_SERVICE}) decouples model selection
from orchestration logic, enabling model substitution without backend changes.
The route labels, such as \texttt{gpt4o} and \texttt{gpt4o-mini}, are names
and not models: in the thesis environment both resolve to the same deployment,
\texttt{gpt-6-luna} (Data Zone Standard, Sweden Central), so the label says
nothing about which model answered.
Because queries are dispatched to models of varying capability and cost, the
dynamic cascade routing and cost-aware model selection evaluated in O3 are
architecturally feasible without redesigning the
service~\cite{chen2023frugalgpt}.
O2 extends this service with Langfuse instrumentation to emit per-invocation
token counts and monetary cost for every provider path.

\paragraph{Vector Database Service (\texttt{chatbot-vector-db}).}
This service owns document ingestion and semantic retrieval.
It loads documents from Azure Blob Storage, splits them with LangChain's
\texttt{RecursiveCharacterTextSplitter}, generates dense embeddings via

\texttt{text-embedding-ada-002}, and stores the vectors in a MongoDB Atlas
Vector Search index.
At query time it supports both pure $k$-nearest-neighbour vector search and a
hybrid mode combining vector similarity with a BM25-like keyword index,
reflecting the Advanced \gls{rag} mechanisms surveyed in
Section~\ref{subsec:rag_survey}~\cite{gao2023ragsurvey}.
The semantic caching layer evaluated in O3 will be integrated at this retrieval
stage, intercepting repeated semantically equivalent queries before the
embedding and \gls{llm} invocation steps, consistent with the GPTCache architecture
of Section~\ref{subsec:semantic-caching}~\cite{bang2023gptcache}.

\paragraph{Datastore Microservice (\texttt{datastore-microservice}).}
This service provides a pluggable transactional data layer for chat history,
session metadata, document records, and suggested questions, toggling between
Azure Cosmos DB and MongoDB Atlas via a single \texttt{DATABASE} environment
variable behind a shared \gls{api} surface.
It is not targeted by any of the four objectives but is an operational
dependency of the backend orchestrator throughout the evaluation experiments.

\paragraph{\gls{mcp} Gateway (\texttt{chatbot-mcp}).}
This service is the artefact introduced by O1.
It is a separate gateway microservice that discovers and invokes the tools of
\gls{mcp} servers, while a tool-use agent in the backend decides which tools a
turn needs.
Because the \gls{llm} microservice returns text only, with no native function
calling, tool selection is prompt-based: the tool catalogue is injected into a
prompt and the model answers with a structured choice.

\subsection{Golden-Path Data Flow}
\label{subsec:golden-path}

The canonical interaction sequence, summarised in
Table~\ref{tab:golden-path}, defines the measurement surface for O2 and the
optimisation targets for O3.

\begin{table}[ht]
\centering
\caption{Maestro golden-path interaction sequence.}
\label{tab:golden-path}
\begin{tabular}{@{}c p{0.82\linewidth}@{}}
\toprule
\textbf{Step} & \textbf{Action} \\
\midrule
1 & The authenticated user submits a query via the Streamlit frontend. \\
2 & The frontend issues \texttt{POST /v1/backend/ai-agent-response} to the
    backend with session, query, and selected provider. \\
3 & The backend retrieves recent conversation history from the datastore. \\
4 & The backend queries the vector database for the top-$k$ similar chunks via
    hybrid retrieval. \\
5 & The backend evaluates the relevance of each retrieved chunk via the \gls{llm}
    microservice; only passages judged relevant proceed. \\
6 & The backend assembles the prompt and issues a generation call via the
    selected provider. \\
7 & The answer and source citations are persisted and returned to the
    frontend as a single response. \\
\bottomrule
\end{tabular}
\end{table}

No token counts, latency measurements, or cost signals were recorded at any
stage of the pre-intervention implementation - the structural gap directly
motivating O2.

\subsection{Connectivity and Protocol Gaps}
\label{subsec:connectivity}

Every external data source or capability in Maestro is currently integrated
through a bespoke REST connector, with no shared discovery or invocation
contract.
The framework has no component through which it could consume external
\gls{mcp}-compliant servers without provider-specific adapter code.
As discussed in Section~\ref{sec:mcp}, the \gls{mcp} defines a
universal JSON-RPC interface through which \gls{llm} hosts discover and invoke
external tools and resources, replacing repeated point-to-point integration
with a standardised, plug-and-play connectivity model~\cite{anthropic2024mcp}.
O1 addresses this gap by introducing a gateway service that lets Maestro
reach external \gls{mcp} servers, and a tool-use agent in the backend that
selects among the discovered tools.

\section{Methodology}
\label{sec:methodology}
% ============================================================

\subsection{Research Approach}
\label{subsec:research-approach}

This work adopts a \textit{Design Science Research} (DSR)
methodology~\cite{hevner2004design}, the standard paradigm for research whose
primary output is an engineered artifact evaluated in a real organisational
context.
DSR prescribes an iterative cycle of problem identification, artifact design,
construction, and rigorous evaluation conducted in close collaboration with the
environment that defines the problem.
This is appropriate here for the same reasons detailed in Section~\ref{sec:objectives} in Chapter~\ref{cha:introduction}: the contributions - an \gls{mcp} integration layer, observability pipeline, cost-reduction mechanisms, and a composable orchestration runtime - must be assessed on the real architecture to establish their validity.
The Maestro services on Microsoft Azure serve simultaneously as engineering
substrate and experimental environment. Experiments run on a dedicated thesis
deployment of the same services, not on a client production system, and the
evaluation data is a replay set of questions rather than live production traffic.
This choice keeps client data out of the thesis and allows the control and
experimental groups to be run under identical conditions.

\subsection{Dependency Ordering and Research Phases}
\label{subsec:phases}

The four objectives are addressed in an order that respects their dependency
structure.
O1 (\gls{mcp} integration) is architecturally independent and proceeds in parallel
with the instrumentation work of O2.
O2 (cost telemetry pipeline) is a \textit{hard prerequisite} for O3: without a
quantitative production baseline of token cost, latency, and output quality
there is neither a principled basis for selecting cost-reduction techniques nor
a reference against which their effect can be measured.
O4 (composable agent graphs) is conditional on O3 being substantially complete.
If pursued, it reuses the Langfuse instrumentation established in
O2 for its trace-coverage evaluation, a deliberate architectural decision that
avoids maintaining parallel instrumentation pipelines, as described in
Section~\ref{sec:genai-ops-governance}~\cite{langfuse2024}.

Each objective follows three phases: \textit{design}, in which the target
architecture and tooling are specified; \textit{implementation}, in which the
artifact is built and integrated into the Maestro production stack; and
\textit{evaluation}, in which the artifact is assessed against the success
criteria of Section~\ref{sec:objectives} using the measurement instruments
described below.

\subsection{Implementation Approach per Objective}
\label{subsec:implementation}

\paragraph{O1 - \gls{mcp} Client Integration.}
An \gls{mcp} client lets Maestro consume external
\gls{mcp}-compliant servers - such as MongoDB Atlas, Microsoft Learn, and Microsoft
Fabric MCP - without bespoke adapter code, relying solely on the \gls{mcp} Python
SDK for protocol-level discovery and invocation~\cite{anthropic2024mcp}.
FastMCP is used only where the gateway itself hosts a server, not in its
client path.

\paragraph{O2 - Unified Cost Telemetry Pipeline.}
Every \gls{llm} invocation path identified in a static audit of the Maestro codebase
is instrumented using Langfuse as the primary \gls{llm} observability
layer~\cite{langfuse2024}.
Each instrumented invocation exports cost per request, a full execution trace,
and - in sampling mode - \gls{ragas} quality scores covering faithfulness and answer
relevance~\cite{es2023ragas}.
Infrastructure-level signals are aggregated through the existing OpenTelemetry
pipeline into Azure Monitor, providing a unified view across \gls{llm} and compute
dimensions.
The resulting cost baseline is validated against the corresponding Azure
billing invoice before any O3 intervention begins, establishing its credibility
as an evaluation reference.

\paragraph{O3 - Cost Reduction via Tokenomics Optimisation.}
The techniques implemented under O3 are selected from the production usage
patterns surfaced by the O2 baseline, following the three-layer tokenomics
framework presented in Section~\ref{subsec:tokenomics-practice}.
A workload exhibiting high query repetition motivates semantic caching,
implemented via MongoDB Atlas Semantic Cache or Azure Managed
Redis~\cite{bang2023gptcache}.
A workload dominated by simple queries motivates cascade routing to smaller
models via LangChain model routing~\cite{chen2023frugalgpt}.
Prompt compression via LLMLingua~\cite{jiang2023llmlingua} is evaluated as a
complementary technique targeting the representation layer.
At least two techniques are implemented and empirically compared.

\paragraph{O4 - Composable Agent Graph Orchestration.}
Maestro's purpose-built orchestrators are refactored as reusable LangGraph
graphs, sharing the Langfuse observability stack established in
O2~\cite{chase2022langchain}.
At least two production workflows with structurally distinct topologies are
refactored - one sequential and one with conditional branching or parallelism -
demonstrating that the LangGraph pattern is expressive enough for diverse
real-world cases.
The refactored graphs are accompanied by unit tests, replacing the untested
hand-crafted implementations.

\subsection{Evaluation Strategy}
\label{subsec:evaluation}

\paragraph{O1.}
The \gls{mcp} integration is validated through automated integration tests that
verify successful invocation of external \gls{mcp} server tools from Maestro, with no
provider-specific adapter code in the invocation path, and is supported by a
proof-of-concept deployment for each integrated external \gls{mcp} server.

\paragraph{O2.}
The telemetry pipeline is evaluated on whether the identified \gls{llm} invocation
paths are instrumented, each invocation exports cost, trace, and sampled \gls{ragas}
scores, and the Langfuse-reported costs reconcile with the Azure billing invoice
before any O3 intervention begins.

\paragraph{O3.}
Cost-reduction effectiveness is measured as the percentage reduction in
cost-per-query relative to the O2 baseline over a replay set of queries
partitioned into a control group and an experimental group.
Quality preservation is evaluated via the Two One-Sided Tests (TOST)
procedure~\cite{lakens_2017_tost} on \gls{ragas} faithfulness and answer relevance
scores.
TOST is adopted in preference to a standard two-sample $t$-test because the
research question is one of \textit{equivalence} - demonstrating that the
experimental and control quality distributions are sufficiently close to be
indistinguishable - whereas a non-significant $t$-test only fails to detect a
difference and cannot, on its own, support a positive claim of quality
preservation~\cite{lakens_scheel_isager_2018}.

\paragraph{O4.}
The orchestration artifacts are evaluated on refactoring at least two workflows
with structurally distinct topologies, achieving substantial Langfuse trace
coverage of execution steps, reducing lines of code relative to the original
hand-crafted implementations, and adding unit tests where the originals had
none.

\subsection{Cost per Query}
\label{subsec:cost-per-query}

Cost per query is the cost of one \texttt{chat-response} trace, that is, of
everything a single user question triggers: the answer generation, the
relevance checks on the retrieved chunks, the \gls{mcp} tool-selection
rounds, and the embedding of the query.
Calls made by side tasks that run outside the turn, such as session
summarisation or sentiment analysis, produce separate traces and are reported as
overhead and not added to the cost per query.
The cost of an \gls{llm} judge used for quality scoring is kept apart in the
same way, so that evaluating a technique does not inflate the figure being
evaluated.

\subsection{Experimental Controls and Validity Threats}
\label{subsec:validity}

The primary threat to \textit{internal validity} in O3 is a change in the
workload between the baseline and the intervention: if the query mix or the
conditions under which queries are issued shift, observed cost differences may
reflect that change rather than technique effectiveness.
Using a fixed replay set removes the drift of live traffic.
The control and experimental groups are further run within the same time
window, stratified to preserve query-type distribution.
Timing matters as well: provider-side prompt caches expire between spaced
turns, so the first call of a turn can pay the cache-write rate again, and
the replay is paced identically in both groups.

The primary threat to \textit{construct validity} is the use of
Langfuse-reported token counts as a proxy for actual cost; this is addressed by
the O2 validation requiring reconciliation with Azure billing data before the
instrument serves as an evaluation reference.
Because the invoice cannot be split by model deployment, and the model resource
is shared with other consumers whose traffic cannot be separated in time, the
reconciliation uses Azure Monitor token counts multiplied by the billed unit
prices; this source is independent of Langfuse, so agreement between the two is
informative.

\textit{External validity} is bounded by the single-environment nature of the
evaluation: all implementation and measurement work is conducted on the Azure
deployment of Maestro.
Architectural patterns and cost-reduction findings are expected to transfer to
equivalent \gls{rag} deployments on other cloud platforms, but cross-environment
equivalence is not empirically validated within the scope of the present work.
